# Experiment 01 raw evidence — 2026-08-23

## Scope

Question: how does one fixed, compute-heavy, element-independent OpenMP loop
scale from one to eight physical CPU cores?

The first full run used the committed default of 8,000,000 elements. Its
near-linear result crossed the pre-recorded `7x` threshold at eight threads.
That result is preserved below. A second run changed only the fixed input size
to 80,000,000 elements so each timed interval was roughly ten times longer;
this was the smallest check for whether short intervals explained the result.

## Environment and commands

```text
Instance: EC2 g4dn.4xlarge
CPU: Intel Xeon Platinum 8259CL at 2.50 GHz
Topology: 1 socket, 8 physical cores, 2 hardware threads per core
Compiler: g++ 13.3.0
OpenMP runtime: GNU libgomp
Compiler flags: -std=c++20 -O3 -march=native -fopenmp
Placement: OMP_PLACES=cores, OMP_PROC_BIND=spread, OMP_DYNAMIC=FALSE
Schedule: static
Timer: omp_get_wtime; reported timer tick 1 ns
Host load before measurement: 0.02, 0.01, 0.00
```

```bash
bash experiments/01_cpu-thread-scaling/run_experiment.sh
ELEMENTS=80000000 REPETITIONS=7 \
  bash experiments/01_cpu-thread-scaling/run_experiment.sh
```

The optimized compiler report identified the measured element loop as
vectorized with 32-byte vectors and a 16-byte fallback. Vectorization settings
were identical for every thread count. A separate compile check with
`-fno-tree-vectorize` produced no vectorized-loop report for this loop; that is
only setup evidence for the later SIMD experiment, not a timing comparison in
Experiment 01.

## Correctness before timing

For both input sizes, the complete one-thread output was computed first. Each
requested OpenMP team then ran once and was compared element-by-element with
the one-thread reference before timing began:

| Threads | Mismatches | Maximum absolute difference |
| ---: | ---: | ---: |
| 1 | 0 | 0.0 |
| 2 | 0 | 0.0 |
| 4 | 0 | 0.0 |
| 8 | 0 | 0.0 |

The program also confirmed that the OpenMP runtime created the requested team
size. An `OMP_DISPLAY_AFFINITY=TRUE` check showed one worker per physical-core
place at eight threads:

```text
core place 0: logical CPUs 0,8
core place 1: logical CPUs 1,9
core place 2: logical CPUs 2,10
core place 3: logical CPUs 3,11
core place 4: logical CPUs 4,12
core place 5: logical CPUs 5,13
core place 6: logical CPUs 6,14
core place 7: logical CPUs 7,15
```

Each place contains the two SMT siblings of one physical core. With at most
eight OpenMP workers and eight places, the runtime assigned one worker to each
place rather than adding a second worker on a physical core.

therefore changed the initial model rather than being tuned toward the expected
`4–6x` range.

## Observation versus interpretation

Observed:

- All correctness checks completed with zero mismatches.
- Both input sizes showed nearly proportional speedup from one through eight
  threads.
- The longer run reached `7.964x` speedup and `99.6%` efficiency at eight
  threads, outside the predicted `4–6x` range.
- The longer run's raw times were tightly grouped; its largest min-to-max span
  was under 0.6% of the median.
- The runtime honored the requested team sizes and exposed eight distinct
  physical-core places.

Interpretation consistent with, but not proved by, those observations:

- The workload was deliberately favorable to scaling: equal independent work,
  static scheduling, no locks or reductions, high arithmetic work per element,
  and one worker per physical core on a single NUMA node.
- Parallel overhead and shared-resource costs may exist, but they were too
  small to produce a material bend in this `1–8` curve.
- This result does not imply that arbitrary CPU preprocessing, memory-bound
  loops, imbalanced tasks, or synchronization-heavy workloads scale linearly.
- No hardware counters, CPU-frequency samples, or memory-bandwidth measurements
  were collected, so the run does not attribute the remaining gap from ideal
  scaling to a particular cause.

The timing surprise is retained as the experiment's main learning evidence.
