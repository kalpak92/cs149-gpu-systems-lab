# Experiment 02 raw evidence — 2026-08-23

## Scope

Question: how much faster does the same compute-heavy,
element-independent loop run on one CPU thread when compiler SIMD
vectorization is enabled rather than disabled?

The scalar baseline and vectorized change used the same source, input,
algorithm, one-thread execution, placement, warm-up policy, repetition count,
and common compiler flags. The only controlled compile-time change was
`-fno-tree-vectorize` on the scalar baseline.

```text
Instance: EC2 g4dn.4xlarge
CPU: Intel Xeon Platinum 8259CL at 2.50 GHz
Topology: 1 socket, 8 physical cores, 2 hardware threads per core
Compiler: g++ 13.3.0
OpenMP runtime: GNU libgomp
Common flags: -std=c++20 -O3 -march=native -fopenmp -Wall -Wextra -Wpedantic

Warm-up: one complete kernel execution before timing each binary
Measurement: 7 kernel-only wall-time samples; median reported
Timer: omp_get_wtime; reported timer tick 1 ns
Host load before measurement: 0.15, 0.16, 0.21
```

The highest-CPU processes observed before measurement were editor tooling at
approximately 4% of one logical CPU each; no competing CPU-heavy workload was
present.

```bash
bash experiments/02_simd-vectorization/run_experiment.sh
```

## Manipulation check before timing

The vectorized compiler report identified the measured expression at source
line 156:

```text
simd_vectorization.cpp:156:68: optimized: loop vectorized using 32 byte vectors
simd_vectorization.cpp:156:68: optimized: loop vectorized using 16 byte vectors
```

The scalar report contained no vectorized-loop entry for that expression. The
runner then restricted disassembly inspection to the OpenMP-outlined measured
kernel. Representative instructions were:

```text
scalar baseline:
vfmadd132ss xmm0,xmm1,DWORD PTR [rsi+rdx*4]
vfmadd132ss xmm0,xmm1,xmm2

vectorized change:
vfmadd132ps ymm0,ymm1,YMMWORD PTR [r9+r8*1]
vfmadd132ps ymm0,ymm1,ymm2
```

`ss` is scalar single-precision floating point. `ps` is packed
single-precision floating point. The main vector path uses a 256-bit `ymm`
register, which holds eight 32-bit `float` elements; GCC also generated a
16-byte fallback path for smaller remaining groups.

## Observation versus interpretation

Observed:

- Both correctness checks passed before timing and the final checksums matched.
- The scalar measured kernel contained scalar float FMA instructions.
- The vectorized measured kernel contained 256-bit packed float FMA
  instructions, representing eight 32-bit lanes.
- Both binaries used one OpenMP worker.
- The vectorized median was `7.881x` faster than the scalar median.
- The result was above the pre-recorded `4x` lower threshold and below the
  `8x` upper threshold.

Interpretation consistent with, but not proved by, those observations:

- This regular workload translated its eight packed float lanes into almost
  eight times the one-thread throughput.
- The result isolates SIMD from Experiment 01's multi-core mechanism: several
  data elements progressed within one instruction stream rather than several
  worker instruction streams running on different cores.
- SIMD width does not universally guarantee proportional speedup. Dependencies
  between iterations, divergent control flow, non-contiguous access, scalar
  work, or another bottleneck can leave lanes unused or make vector arithmetic
  only part of total execution time.
- No CPU-frequency samples or hardware counters were collected, so this run
  does not identify the cause of the small remaining gap from exactly `8x`.

The result stayed within both pre-recorded thresholds, so no threshold-driven
follow-up was added to this experiment.
